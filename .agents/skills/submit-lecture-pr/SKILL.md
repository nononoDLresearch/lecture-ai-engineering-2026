# 各回の提出 PR

対象回の課題作業が完了したら、提出しないという明示的な指示がない限り使う。このリポジトリの `README.md`、`AGENTS.md`、`lectures/NN/problem.md` を先に確認する。提出準備は自動で進めてよいが、commit と push は別々に本人の確認を待つ。

## 提出前に確認すること

- 対象回 `NN`、作業ブランチ `lecNN`、提出ファイル `lectures/NN/answer.md` を特定する。回ごとの追加提出物は `problem.md` に従う。課題の実装と記録が未完了なら、できる範囲まで仕上げてから提出する。
- `git status` と差分を確認し、対象回に関係する変更だけを提出する。既存の未コミット変更を勝手に捨てたり、他の回や無関係なファイルを巻き込んだりしない。秘密情報や個人の学習ログを含めない。
- `worklogs/NN.md` に今回の作業と確認結果を追記する。PR には対象回の作業ログを含めてよいが、`learning_log/` は含めない。作業ログは `answer.md` の代わりにしない。
- コード変更があれば関係する動作を確認し、原則 `uv run pytest -q` を実行する。実行できなかった確認や残る課題は PR 本文に正確に記す。
- `origin` と GitHub CLI の認証先を確認する。base repository が本人の fork であることを確かめる。講座本体 `matsuolab/lecture-ai-engineering-2026` へは作成しない。

## 確認を得て PR を作る・更新する

1. 対象回の作業ブランチで、提出する変更だけを stage し、差分・コミットメッセージ案・PR 本文案を用意する。ブランチが未作成なら、対象回の `problem.md` に従って作る。既存コミットを勝手に書き換えない。
2. **commit の直前に**、対象ブランチ、stage 済みのファイルと変更概要、コミットメッセージを本人に示し、commit してよいか明示的に確認する。承認の返答があるまで commit しない。依頼時の「PR を作って」という指示を、この確認の代わりにしない。
3. commit 後、**push の直前に**、コミット ID、送信先の fork とブランチ、PR の base を本人に示し、push してよいか改めて明示的に確認する。承認の返答があるまで push しない。commit の承認を push の承認と兼ねない。
4. push 後、同じ head と base の PR がすでにあれば、その PR の本文を必要に応じて更新する。なければ `gh pr create` で **base repository は自分の fork、base branch は `main`** と明示して作成する。CLI の既定値だけに頼らず、作成後に PR の head・base を確認する。
5. タイトルは `第N回 演習・宿題` を基本にする。本文には、取り組んだ演習と宿題のレベル、主な変更・観察結果、実行した確認と結果、未完了事項があればその範囲を簡潔に書く。数値や実行結果を推測で補わない。
6. PR の URL と、提出したブランチ・確認結果を報告する。`gh` がない場合は利用可能な認証済み GitHub ツールを使う。PR 作成手段がない場合や認証・ネットワークの問題で作成できなければ、準備済みのブランチと未完了の操作を明示する。失敗した外部操作を無制限に繰り返さない。

確認が得られない、または本人が見送る場合は、その段階で止める。時間経過や無回答を承認とみなさない。変更内容や送信先が確認後に変わった場合は、該当する操作の前に確認を取り直す。

PR 本文の複数行テキストは一時ファイルに書いて `gh pr create --body-file` または `gh pr edit --body-file` へ渡す。
